# C.I. #01 — Citation Remediation Payload Generator

**Deterministic AI citation remediation from supplied evidence and HTML snapshots.**

[Run on Apify](https://apify.com/bono718/citation-remediation-payload-generator) · [Capability portfolio](../README.md)

## The problem it solves

An AI answer cites a competitor but omits your page, even though the relevant facts already appear in your HTML. This capability turns that supplied citation gap into a machine-readable remediation payload: proposed HTML and WebPage JSON-LD additions, snapshot checks, and acceptance tests.

It can be used in generative engine optimization (GEO), answer engine optimization (AEO), and AI search visibility workflows where an upstream system already supplies the answer, cited URLs, and page snapshots. It prepares changes for a downstream consumer; it does not guarantee that an AI system will cite the page.

## Complete input example

Save this as `input.json` for the API example below. Supply one target page, one competitor page, and one query per run. Unknown input fields are rejected.

```json
{
  "targetUrl": "https://example.com/product",
  "competitorUrl": "https://competitor.example/product",
  "query": "Does Acme export CSV?",
  "evidence": {
    "answer": "The competitor offers CSV exports.",
    "citedUrls": ["https://competitor.example/product"]
  },
  "targetHtml": "<!doctype html><html><body><h1>Acme</h1><p>Acme exports reports in CSV format.</p></body></html>",
  "competitorHtml": "<html><body><h1>CSV exports</h1></body></html>",
  "facts": [{
    "text": "Acme exports reports in CSV format.",
    "sourceUrl": "https://example.com/product"
  }]
}
```

For this example, the documented behavior is a `ready` payload with a proposed HTML section, minimal WebPage JSON-LD, and acceptance tests. This is a remediation plan, not proof of future citation uplift.

## Machine contract

**Inputs:** target URL, competitor URL, query, supplied citation evidence, both HTML snapshots, and grounded facts.

**Outputs:** versioned JSON containing `schemaVersion`, `inputHash`, `status`, diagnosis, snapshot provenance, proposed changes, preconditions, acceptance tests, and warnings. Possible statuses include `ready`, `no_gap`, and `no_action`. Consumers should inspect the status and warnings before applying changes.

| Operation or test | Purpose |
|---|---|
| `append_html` | Propose an HTML addition grounded in supplied facts |
| `append_json_ld` | Propose minimal WebPage structured data |
| `selector_count` | Check the expected number of matching elements |
| `text_contains` | Check for expected text |
| `json_ld_webpage_url` | Check the WebPage URL in JSON-LD |

Acceptance tests are typed data, not arbitrary executable code. A downstream consumer must verify snapshot hashes and selector preconditions, track applied change IDs, prevent duplicate application, and support rollback.

## Operational boundaries

- No live page fetching, JavaScript rendering, or citation collection.
- No ranking prediction, citation uplift guarantee, or semantic authentication of supplied evidence.
- No direct website edits, CMS writes, or bulk processing.
- Grounded excerpt matching establishes occurrence in the supplied snapshot, not factual truth or relevance.
- Minimal WebPage JSON-LD does not establish eligibility for Google rich results.
